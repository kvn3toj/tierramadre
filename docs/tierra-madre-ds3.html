Heurísticas

  • La jerarquía de texto usa los cuatro niveles (text → muted → subtle → disabled). Dos niveles = jerarquía plana = rediseñar.
  • La esmeralda nunca es fondo de un área mayor que un chip. Grandes áreas verdes compiten con las piedras.
  • success ES la esmeralda — no existe un segundo verde.
  • El color nunca es el único indicador: siempre icono o etiqueta acompañante.
  • Cero hex nuevos en código de features — todo traza a --tm-*.

Fundación 04

Movimiento

Silencioso y seguro. cubic-bezier(.22, 1, .36, 1) · 160 / 240 / 420ms. Sin resortes ni rebotes en la UI del producto.

Hover quieto

borde se enfatiza — 160ms, sin mover layout

Capa que flota

transform + sombra — 240ms, solo GPU

  • Solo se animan transform y opacity — nunca width/height/top/left.
  • prefers-reduced-motion es una puerta dura: todo colapsa a instantáneo.
  • Anti-parpadeo es ley: caché síncrono en useState(() => …), espacio reservado con aspect-ratio, keys únicas por instancia, precarga de galerías, swap instantáneo sobre fade, #t=0.001 para video iOS.
  • Todo skeleton replica la geometría final — el contenido nunca salta al llegar (CLS ≈ 0).
Arquitectura 01

Shell y Navegación

La app es un shell de viewport fijo: body jamás hace scroll; el único scroller de página es <main id="main-content">. Su altura medida se publica como --app-main-height — las alturas se derivan, nunca se adivinan.

Wayfinding

  • Toda pantalla se declara en el registro PageConfig — título, modo, back. El fallback anónimo es un error de lint, no una feature.
  • Back es sagrado: siempre vuelve a donde el usuario estaba — con su scroll — o a la raíz de familia en deep links. Nunca cambia de familia sin anuncio.
  • Raíces de familia usan título large serif; descendientes, compact. El detalle titula con el nombre de la pieza.
  • Tab bar = lugares; sheets = verbos. El tab bar nunca muta datos.
  • Desktop ≥1180px: misma arquitectura proyectada como top-nav + breadcrumbs. Una sola IA.
  • Todo deep link (/p/:itemId) aterriza con chrome, título y back correctos.
Arquitectura 02

Las diez leyes del scroll

  1. Un scroller por vista. Nada más scrollea salvo nested-scrollers deliberados.
  2. Todo nested scroller va contenido — containedScrollY/X; un overflow:auto desnudo es error de lint. Los gestos de borde jamás encadenan hacia <main>.
  3. Las alturas se miden, no se adivinan. paneHeight() / --app-main-height. Esto mata el bug del catálogo: HEADER_OFFSET = 280 y minHeight: 600 se reemplazan por altura medida → la grilla termina exactamente sobre el tab bar y muere la sensación de "dos scrollbars peleando".
  4. La posición de scroll es memoria. Back/forward restaura el offset del elemento que realmente scrolleaba; navegación nueva resetea al tope. Quien vuelve de un producto aterriza en la fila que dejó.
  5. El chrome fijo nunca come contenido — reservas tokenizadas, últimas filas siempre alcanzables.
  6. Sheets en dvh (85dvh + fallback), scroll interno contenido, última fila sobre el home indicator.
  7. scroll-behavior: smooth vive solo en html, con reduced-motion. Nunca en *.
  8. Sin touch-action en scrollers. El global de controles es el único del app.
  9. Scrollers horizontales: containedScrollX (mata el back-swipe hijack) + affordance visible en ambos extremos.
  10. Performance: virtualizar listas >50; solo listeners pasivos; shrink de headers via transform.

Gobernanza

Checklist por pantalla

  1. Vitrina — ¿la esmeralda es lo único saturado?
  2. Un scroller — ¿exactamente un elemento scrollea?
  3. Retorno — ¿volver conserva scroll, sin flash?
  4. Entrecerrar — ¿jerarquía sí, gritos no?
  5. Estados — ¿loading / empty / error / content diseñados?
  6. Pulgar — ¿nada destructivo abajo; targets ≥ 44px; última fila libre?
  7. Tokens — ¿cero hex/px/z literales en el diff?
  8. Reduced motion — ¿todo usable sin animación?
  9. 375px — ¿sin scroll horizontal; body ≥ 17px; sobrevive iPhone SE?
  10. Chrome — ¿un top y un bottom chrome según la matriz?
